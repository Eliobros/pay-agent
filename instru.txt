PAYAGENT — ENGINEERING IMPLEMENTATION

You are acting as a Senior Full-Stack Engineer, AI Engineer, and Fintech Security Architect.

Your task is to improve an existing project called PayAgent.

Do not rebuild the project from scratch.

First, inspect the entire existing codebase, understand its architecture, identify existing features, and implement the improvements described below while preserving all currently working functionality.

1. PROJECT OVERVIEW

PayAgent is an open-source AI-powered autonomous sales agent designed for online stores.

Its purpose is to allow any online store to integrate an AI sales assistant using a single JavaScript script.

Customers can:

- Search for products through natural language.
- Receive personalized product recommendations.
- Purchase products through PayPal.
- Check order statuses.
- Request refunds through conversational AI.

Store owners maintain control over sensitive financial operations.

Technology stack:

- Frontend: Next.js.
- Backend: Python FastAPI.
- Database: SQLite (existing implementation).
- Payments: PayPal REST API (Sandbox).
- AI: OpenAI-compatible API with tool calling.
- Persistence: Existing database architecture.

Preserve the existing technology stack unless a change is absolutely necessary.

2. OWNER AUTHENTICATION

Implement a secure authentication system for store owners.

Requirements:

- Owner registration or secure account provisioning.
- Login and logout.
- Secure password hashing using Argon2id or bcrypt.
- Secure session management using HTTP-only cookies.
- Protection against unauthorized access to /owner and administrative APIs.
- Authentication middleware for protected endpoints.
- Session expiration.
- Rate limiting for authentication endpoints.

Never expose ADMIN_TOKEN, database credentials, payment secrets, or authentication secrets to the frontend.

Replace the existing demo authentication mechanism with proper authentication.

3. PAYMENT CREDENTIAL MANAGEMENT

Create a payment configuration section in the owner dashboard.

Store owners should be able to configure their payment provider credentials through the dashboard instead of manually editing environment variables.

Initial provider:

PayPal Sandbox.

Required fields:

- Client ID.
- Client Secret.
- Environment (Sandbox/Live).

Security requirements:

- Never return complete secrets to the frontend after saving.
- Encrypt sensitive credentials using AES-256-GCM.
- Keep the encryption master key outside the database.
- Use authenticated encryption with proper nonce and authentication tag handling.
- Never log secrets.
- Validate credentials before marking a provider as operational.

IMPORTANT:

Do not use bcrypt to encrypt credentials. Password hashing and reversible secret encryption are different operations.

Keep global infrastructure secrets in environment variables.

Design the payment configuration architecture to support future providers such as M-Pesa and e-Mola.

4. PAYPAL WEBHOOK SYSTEM

Implement a robust PayPal webhook integration.

Requirements:

- Create a webhook endpoint in FastAPI.
- Verify webhook signatures using PayPal's official verification mechanism.
- Reject invalid webhook notifications.
- Handle payment capture events.
- Handle refund events.
- Update order statuses based on verified events.
- Store processed webhook event IDs.
- Prevent duplicate event processing.
- Maintain transaction logs.

The webhook system must be idempotent.

Repeated delivery of the same event must never result in duplicate financial operations.

Do not trust frontend payment confirmation.

Only verified PayPal responses and validated webhook events should establish authoritative payment status.

5. FINANCIAL IDEMPOTENCY

Implement idempotency for all financial operations.

This includes:

- PayPal order creation.
- Payment capture.
- Refund processing.

Requirements:

- Generate unique idempotency keys.
- Store operation identifiers.
- Prevent duplicate captures.
- Prevent duplicate refunds.
- Handle retries safely.
- Use database transactions where appropriate.
- Handle concurrent requests correctly.

A failed or repeated request must not accidentally charge a customer twice.

Each order must only be refunded up to its captured refundable amount.

6. REFUND MANAGEMENT — HUMAN APPROVAL

This is one of PayAgent's most important features.

The AI must NOT independently approve damage-related refund requests.

Implement a complete refund request workflow.

Customer workflow:

1. Customer requests a refund through the AI chat.
2. The AI identifies the relevant order.
3. The backend validates order ownership and refund eligibility.
4. The customer provides a reason.
5. The customer uploads supporting evidence.

Supported evidence:

- JPEG images.
- PNG images.
- WebP images.
- MP4 videos.
- WebM videos.

Limits:

- Maximum video duration: 60 seconds.
- Configurable maximum file size.
- Validate actual file content, not only file extensions.
- Reject unsupported or dangerous file types.

Store evidence privately.

Never expose private evidence through publicly accessible storage URLs.

Owner dashboard:

Create a Refund Requests section inside /owner.

Each request must display:

- Refund Request ID.
- Order ID.
- Customer identifier.
- Product name.
- Amount originally paid.
- Refund amount requested.
- Purchase date.
- Request date and time.
- Customer's explanation.
- Uploaded photographs.
- Uploaded videos.
- Current request status.

Owner actions:

- Approve Refund.
- Reject Refund.
- Request Additional Evidence.

IMPORTANT FINANCIAL RULE:

Only the authenticated store owner can approve or reject damage-related refund requests.

The AI can collect information and communicate decisions, but it cannot determine whether evidence is authentic.

The owner must personally inspect the submitted photographs and videos.

After approval:

1. Validate the approval.
2. Verify that the payment was captured.
3. Verify that the amount is refundable.
4. Execute the PayPal refund.
5. Verify the result.
6. Update the database.
7. Notify the customer.

Do not mark a refund as completed before receiving confirmation from PayPal.

Implement refund statuses:

- REQUESTED
- WAITING_EVIDENCE
- UNDER_REVIEW
- MORE_EVIDENCE_REQUIRED
- APPROVED
- REJECTED
- PROCESSING
- REFUNDED
- FAILED

Maintain an audit trail of owner decisions.

7. PERSISTENT CHAT HISTORY

Implement persistent conversation storage.
